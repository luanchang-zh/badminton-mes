# 多租户知识库 HTTP 服务入口（P2）

## 能力概述

本能力回答一个问题：**同一个进程里怎么安全地同时对外提供多个租户的 LightRAG 接口。**

P1 已经能按配置装配出每个租户独立的 `LightRAG` 实例与上传目录；本能力在此之上把它们挂到
`/tenant/{user_id}` 前缀下，用一个 lifespan 统一启停，用一把共享信号量限制模型并发，并确保只有持有内部密钥的
业务服务能访问租户路由。

能力边界是「服务入口层」：应用构建、路由注册、生命周期、限流与鉴权。不含真实存储、真实模型与跨租户隔离验证。

## 需求

### R1：按租户注册带前缀的路由

系统 MUST 在应用构建阶段，为配置中的每个租户把官方三个路由工厂注册到 `/tenant/{user_id}` 前缀下，
不得在运行期增删路由。

约束：

- 复用官方工厂，签名与 v1.5.7 一致：`create_document_routes(rag, doc_manager, api_key)`、
  `create_query_routes(rag, api_key, top_k)`、`create_graph_routes(rag, api_key)`；
- 每个租户注册 33 条路由（文档 18、查询 3、图谱 12），各租户数量相同；
- 不得同时存在未加前缀的 `/documents/*`、`/query`、`/graphs` 路由。

Scenario: 两个租户各自拥有独立前缀
  假设配置中有 2 个租户，user_id 分别为 user_1 与 user_2
  当构建应用并读取路由表
  那么存在 `/tenant/user_1/...` 与 `/tenant/user_2/...` 两组路由
  并且每组都包含 33 条路由
  并且两组路由数量相同
  并且不存在未加租户前缀的 `/documents/upload`、`/query`、`/graphs`

### R2：启动入口与静态路由检查

系统 MUST 提供单一启动入口，支持在不连接数据库、不调用模型的前提下打印完整路由表。

约束：

- 入口参数至少包含 `--config`、`--host`、`--port`、`--print-routes`、`--docs`；
- 入口在导入任何 `lightrag.api.*` 模块之前固定上游配置，避免上游 argparse 抢占命令行；
- `--print-routes` 只构建应用并打印路由，不启动服务、不执行 lifespan、不连数据库、不调模型。

Scenario: 打印两组前缀路由
  当执行启动入口并启用 print-routes
  那么输出包含 2 个租户各自的前缀路由
  并且每条路由都带 `/tenant/<user_id>` 前缀
  并且整个过程没有建立数据库连接、没有调用模型

Scenario: 非法租户配置时拒绝启动
  假设配置中存在重复的 workspace，或环境中设置了 POSTGRES_WORKSPACE
  当执行启动入口并启用 print-routes
  那么进程以非 0 退出码结束
  并且不打印任何路由

### R3：内部密钥鉴权

系统 MUST 要求租户路由携带正确的内部密钥，未携带或携带错误密钥的请求必须被拒绝。

约束：

- 内部密钥由 `LR_INTERNAL_API_KEY` 提供，并作为 `api_key` 传给三个路由工厂（对应 `X-API-Key`）；
- 未配置密钥时，服务只允许绑定回环地址；
- 禁止上游白名单覆盖租户前缀：`WHITELIST_PATHS` 命中 `/*` 这类全通配时必须拒绝启动。

Scenario: 缺少或错误的密钥被拒绝
  假设服务已配置内部密钥
  当请求任一租户路由但不带 X-API-Key
  那么响应状态为 401 或 403
  当请求任一租户路由但携带错误的 X-API-Key
  那么响应状态为 401 或 403

Scenario: 正确密钥可以访问
  假设服务已配置内部密钥
  当请求任一租户路由并携带正确的 X-API-Key
  那么响应状态不是 401，也不是 403

Scenario: 全通配白名单被拒绝
  假设 WHITELIST_PATHS 被配置为通配全部路径
  当启动服务
  那么服务拒绝启动
  并且错误信息指出白名单会绕过租户鉴权

### R4：统一生命周期

系统 MUST 用一个 lifespan 管理全部租户实例的启停，保证每个实例各初始化与释放一次，共享状态只清理一次。

约束：

- 启动：先创建唯一的后台任务集合，再逐个初始化各实例存储；
- 启动阶段任一实例失败时中止启动，并按逆序释放已初始化的实例；
- 关闭：先等待全部后台任务结束，再逐个释放实例存储，最后只清理一次共享状态；
- 后台任务集合全应用共享，不按租户拆分等待。

Scenario: 每个实例各初始化与释放一次
  假设应用中有 2 个租户实例
  当应用启动后再关闭
  那么每个实例的存储初始化恰好发生一次
  并且每个实例的存储释放恰好发生一次
  并且共享状态清理恰好发生一次

Scenario: 释放发生在后台任务结束之后
  假设关闭时仍有后台任务在运行
  当应用关闭
  那么实例存储释放发生在等待后台任务结束之后

### R5：全局模型并发上限

系统 MUST 让所有租户共享同一个模型并发上限，在模型调用层限流，而不是在上传接口限流。

Scenario: 并发调用不超过上限
  假设全局模型并发上限为 N
  当同时发起多于 N 个模型调用
  那么任一时刻正在执行的调用数量不超过 N
  并且全部调用最终都完成

Scenario: 未配置上限时退化为直通
  假设没有配置全局并发上限
  当并发发起多个模型调用
  那么调用不被限流阻塞
  并且全部调用都成功完成

## 错误处理

- 租户配置非法：拒绝启动，以非 0 退出码结束，且不注册任何路由。
- 内部密钥缺失且监听非回环地址：拒绝启动并说明原因。
- 白名单会绕过租户鉴权：拒绝启动并说明原因。
- 启动阶段存储初始化失败：终止启动并按逆序回滚已初始化实例。

## 非范围

- 真实数据库、真实模型与跨租户数据隔离验证（P3）。
- 应用容器镜像、进程守护、多 worker 与反向代理。
- Ollama 兼容接口与 WebUI 静态资源路由。
- Java 业务接入与前端（P4、P5）。
